# SQLite and PostgreSQL portability contract

Status: integrated schema v15 is verified on SQLite and PostgreSQL 17, including
profile ownership, device tokens and the offline SQLite-to-PostgreSQL transfer. Go
repositories run explicit SQL through sqlx; Python repositories use SQLAlchemy
expressions or text SQL with named parameters. Queries are written once in the
SQL both engines accept and are sent as written: no statement is rewritten at
runtime. The whole Go and Python test suites run on both backends.

The same musik build and logical schema must run on SQLite or PostgreSQL. Selecting a backend must not change API behavior, account/profile isolation, queue ordering, recommendation outcomes, migration safety, or worker behavior. SQLite remains the default and supported deployment; PostgreSQL is an optional backend.

## Current boundary and portability gaps

- Go opens one `database/sql` pool (modernc SQLite or pgx) behind a small sqlx wrapper (`player/internal/db/sqlx.go`). Repository SQL uses `?` placeholders, which sqlx rebinds for the driver; nothing else in the statement changes. The few real dialect differences are `Dialect` methods (`HourUTC`, `DateUTC`, `LockForUpdate`) visible at the call site.
- Every personal-data query binds `profile_id` explicitly (`Store.ProfileID` in Go, `conn.profile_id` in Python). There is no implicit profile token. `Store.ForProfile` returns a view of the same pool for another profile.
- Python runtime repositories use SQLAlchemy sessions. Catalog and job operations use mapped entities and SQLAlchemy expressions; other queries are `text()` SQL with named parameters (`:profile`, `:track_id`) through `ORMConnection`, sent unchanged.
- Time windows are computed in application code and compared as UTC ISO-8601 text (whole-second cutoffs order correctly against `Z` and `+00:00` suffixes). Upserts qualify the target table on the right-hand side of `DO UPDATE SET` (`t.col + excluded.col`); PostgreSQL rejects the unqualified form as ambiguous.
- Python runtime connections are SQLAlchemy sessions. The remaining direct `sqlite3` usage is limited to legacy migrations, SQLite snapshot/transfer checks, and SQLite-specific test setup.
- Alembic owns migration history through `musik_15`. Go requires that shared head and additionally checks `PRAGMA user_version` on SQLite; it does not migrate at startup.
- Tests: the Go fixture `player/internal/testdb/schema.sql` is generated from the migrations (`scripts/go_test_schema.py`; a Python test rejects drift). `MUSIK_TEST_BACKEND=postgres` runs the whole Go and Python suites against per-test clones of a migrated PostgreSQL template; CI runs both backends. A repository smoke test reaches every Go repository method.
- Known gap: `profile_id` columns still carry the owner profile as a column DEFAULT inherited from the SQLite adoption migration. Repositories always bind the profile, but the default should be dropped in a later migration so a forgotten value fails instead of landing in the owner's profile.

## Required architecture

### Domain, ORM and repository boundary

- Go uses sqlx over `database/sql` for backend creation, query execution and transactions; Python uses SQLAlchemy sessions, mapped models, expressions and named-parameter text SQL. Both share one pool per process.
- Repositories own SQL and transaction boundaries. Use interfaces by use case (catalog, playback, profile, library jobs, migrations), not one generic CRUD abstraction and not a generic SQL-builder leaking into services.
- The Python worker has its own SQLAlchemy persistence port. It must not bypass the selected backend through `sqlite3.connect` in a command, job or helper path.
- The application receives a storage configuration at startup and constructs one backend. Go player, Python worker, CLI and migration command must resolve the same backend and database identity; secret DSNs are never logged.
- The canonical migration metadata owns the shared schema. Mapped records cover active repository boundaries; the full table-by-table ORM mapping comparison remains a useful follow-up as additional legacy queries become mapped expressions.
- Stable application IDs for users, external identities, profiles and sessions are UUID text generated by the application. Existing track/catalog numeric IDs may remain integer identity values, provided inserts use a portable returned-ID contract and callers do not depend on driver `LastInsertId`.

### SQL and type contract

- Keep the logical schema equivalent. Backend-specific DDL and query forms are allowed inside adapters/migrations; product behavior is not backend-specific.
- Bind parameters through the selected driver's supported mechanism. Do not rewrite SQL placeholders with blind string replacement. Dynamic filters, pagination and sorting are assembled from trusted query parts and bound values.
- Pass time values from application code in UTC. Avoid `datetime('now')`, SQLite date modifiers and lexical assumptions about timestamp strings. Both adapters normalize stored instants to UTC `time.Time` / aware `datetime` at the repository boundary.
- Booleans, nullable values and generated IDs have explicit adapters. SQLite's integer booleans and PostgreSQL `BOOLEAN`, null scanning, and insert return behavior must not leak into domain code.
- Versioned JSON documents are validated at read/write boundaries. Use JSON/JSONB only where a field is queried structurally; do not make JSON extraction functions a cross-backend dependency. Embedding vectors remain versioned binary payloads with documented dimension, numeric encoding and byte order.
- Use equivalent upsert behavior for both engines. Do not depend on conflict clause row counts to infer an insert/update unless the repository normalizes that result.
- Database constraints, not only handler checks, enforce unique identities and foreign-key ownership. Configure foreign keys on every SQLite connection; define corresponding PostgreSQL constraints.

### Transaction and concurrency contract

- A repository method that represents one domain operation documents and owns its transaction. Partial writes are never visible.
- SQLite keeps WAL and a bounded busy timeout; write transactions use the existing immediate-lock behavior where read-then-write atomicity is required. PostgreSQL uses row/unique locks and bounded transaction retries only for explicitly retryable serialization/deadlock errors. Account role/status changes lock the shared `installation_state.active_admin_guard` row before counting admins, so updates to different accounts serialize.
- Worker job claiming is atomic and exclusive under concurrent workers on both engines. Implement engine-specific claim SQL behind one method (SQLite transaction/update; PostgreSQL may use `FOR UPDATE SKIP LOCKED`). A job can never be claimed twice or silently lost.
- No long-lived transaction spans audio processing, model inference, HTTP requests or user playback.
- In-memory indexes/taste caches are derivative state. Their keys include profile IDs where data is personalized, and startup/reload rebuilds them from the chosen backend.

## Migration and configuration contract

- One migration command is the only schema writer. Applications and workers validate schema compatibility and fail clearly; they do not race to migrate at startup.
- Alembic over SQLAlchemy is the sole migration runner. Operator runs `musik db migrate` once before player/worker startup. It adopts existing SQLite v5 data and advances it through identity/profile migrations to v15; Go validates the same head and never migrates at startup. Downgrade is not supported for data migrations; restore a verified backup to roll back.
- SQLite batch DDL and PostgreSQL constraints may use different operations as long as they preserve the same logical invariant. Fresh PostgreSQL databases are created from the reflected shared schema and advanced to the same `musik_15` head.
- The offline `musik db transfer` path copies the complete SQLite v15 schema and rows, including profile-bound device-token hashes, to a destination with only the expected bootstrap owner/profile. It validates the read-only source snapshot, schema and foreign keys, then compares per-table counts and deterministic checksums. It leaves the SQLite source and external music/artwork files untouched; referenced paths must already exist at the destination.
- Existing personal rows are mapped once to the installation owner/default profile before transfer. New invite-created OIDC accounts receive separate users and profiles; the transfer does not copy personal data to them.
- Configuration contract: `MUSIK_DATABASE_URL` selects the backend (`sqlite:///...` or a PostgreSQL URL). Keep `MUSIK_DB_PATH` as a deprecated SQLite-only alias during transition; setting both is an error. Redact credentials from logs and diagnostics.
- SQLite and PostgreSQL use the same schema version, migration identity, account/profile model and logical defaults. PostgreSQL is not a separate product mode.

## Cross-workstream contract with multi-user/profile design

- IDs for `UserID`, `ProfileID`, external identities and revocable sessions are opaque text UUIDs on both engines. Never derive ownership from SQLite rowids or database sequence values.
- Shared installation/catalog data remains unowned. Every personal repository method takes `ProfileID`; profile ownership is checked in the same transaction. The DB portability work must support the profile schema and constraints in both dialects.
- The multi-user/profile branch must not introduce raw SQL or schema assumptions outside this contract. The database branch must not encode OIDC provider, user role, or profile-selection policy in driver code.
- To minimize cross-branch conflicts, keep identity/profile migrations in a distinct versioned migration unit and API/domain contracts independent of engine-specific types. Integration order is: agree on these contracts, establish the store/migration boundary, then add identity/profile persistence against that boundary; both conformance suites stay required.

## Behavioral conformance contract

Run the same repository and service contract cases against SQLite and PostgreSQL fixtures:

1. CRUD, nullable fields, ordering, filtering and pagination return the same values, including Unicode text and timezone boundaries.
2. Upserts preserve update semantics, timestamps and uniqueness outcomes; returned IDs match inserted logical objects.
3. Multi-write operations roll back completely after an injected failure.
4. Two independent connections performing concurrent updates, event de-duplication and job claims preserve the same invariants; no lost update or duplicate claim occurs.
5. Profile-scoped reads/writes cannot cross owner boundaries; catalog data remains shared as specified.
6. Fresh install, migration from SQLite v5 through v14, migration on PostgreSQL, migration of profile ownership and device-token tables, restart after an interrupted migration, and schema-version mismatch fail/complete as documented.
7. Python worker scan, embedding, recommendation-job and event persistence use the selected backend and produce the same logical rows as the Go player.
8. Backup/restore and health/readiness checks succeed for both backends; health output never exposes the database URL.

## Resolved architecture choices

- Resolved: Go uses sqlx with explicit SQL (GORM was removed: most queries are analytical and ran through raw SQL anyway), SQLAlchemy is the Python data layer, Alembic owns migrations, and `musik db migrate` is the operator command. No runtime SQL rewriting.
- Implemented for schema v15: offline SQLite-to-PostgreSQL transfer verifies row counts and SHA-256 checksums and maps the legacy owner/profile. Device-token hashes and profile binding transfer with the database; raw secrets are never stored. Music and artwork files remain external; database rows and embedded binary payloads are transferred.
- PostgreSQL 17 is the CI and release minimum. SQLite requires a version supporting the migration's `RETURNING` behavior.
- SQLite in-memory test compatibility and PostgreSQL CI service image/version are implementation choices; the behavioral cases above are mandatory regardless of tool.
